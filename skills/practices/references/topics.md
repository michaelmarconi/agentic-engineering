# Practice topics

The topics `/practices` suggests. They are not a complete list: any other topic the person asks for, such as how decisions are approved, gets a topic file and a line in the core in the same way. The overview shows each topic as recorded, not recorded yet or out of step with the repository, and suggests the one that matters most now. Within a topic, it reads the repository first, proposes what
it finds, and asks only what it cannot find. Where an answer is long, it goes in a topic file;
otherwise it is a line in the core. A choice between alternatives goes to `/adr`.

| # | Topic | Asks | Usually ends up |
|---|---|---|---|
| 1 | Setting up | What a fresh copy needs: tools, services such as a database, local config; any machine or operating system the work needs; where secrets live; where the project keeps its commands, if it has a command runner or one scripts folder; the command that sets it up | Check your work, Rules |
| 2 | Checking work | The exact commands: all tests, one test file, lint and format, type check; which ones run before every commit | Check your work, Rules |
| 3 | Testing | Test-first or not; what each change must be tested with; coverage and any minimum; end-to-end tests and when they run; test data; what to do with a flaky or slow test | Rules (test-first), `testing.md` |
| 4 | Branches and commits | Branch names; commit message style; whether work may be committed straight to the default branch; how long a branch may live and how often it is merged back, such as merging to the default branch at least daily with three or fewer active branches (trunk-based development) | Rules |
| 5 | Delivering work | How work is split: vertical slices that each leave the product usable, or larger pieces; how big one plan may be, measured by what a person can review, such as one plan per pull request; how many finished builds may wait for a person's review at once; what done means beyond the merge checks, such as deployed or behind a feature flag | Rules, or `delivery.md` |
| 6 | Reviews and merging | Pull requests or not, and the sections every description holds (a template on GitHub); who reviews; how work is merged; what must pass before merging; whether `/agentic:verify` must run and pass on a build before it is merged | Rules, or `merging.md` |
| 7 | CI/CD | Where the pipeline is defined and what it runs on each push, pull request and release; which of its checks are required and which optional; if there is none yet, what it must run (which service to use is an ADR); how to run the same checks locally before pushing; when a run fails: read its log, reproduce the failure locally and fix the cause, re-run at most once and only to rule out a fault outside the change, never skip or disable a test to get green; who may change the pipeline files, and whether agents may | `ci.md`, Rules |
| 8 | Releasing | Required, under these exact headings, each holding something: `## What may be released` (which branches, and whether the code must be merged first); `## Version and its commit` (the scheme, the files that hold it, how a release is tied to one exact commit, such as a tag); `## Publish` (one command, which may take `{version}`, `{commit}` and `{notes}`, a file holding the release notes; or a line starting "None:", such as "None: the merged commit is the release" or "None: the pipeline publishes it"). Optional: `## Release notes` (where and in what form), `## When to release` (after each merge or batched), `## Where it runs` (the machine, and where its credentials live), `## Undoing a release`. `/agentic:release` relies on it | `releasing.md`, with the pointer "before releasing: `docs/practices/releasing.md`" |
| 9 | Deploying | One `## Environment: <name>` section per environment, each with these exact headings, each holding something: `### Releases allowed` (which releases may go there, such as only those already on staging); `### Deploy` (one command, or "None: merging deploys it"); `### Check` (one command that only reads, exits 0 when the product works, and how long to wait for it); `### Roll back` (one command, or "None: stop and tell me"). Optional, at the top: `## Where it runs` (the machine, and where its credentials live), `## How deploys start` (by hand or by the pipeline, and by whom). `/agentic:deploy` relies on it | `deploying.md`, with the pointer "before deploying: `docs/practices/deploying.md`" |
| 10 | Database changes | How they are written and applied; whether they must be reversible | `database-changes.md` |
| 11 | Security and dependencies | Before adding a dependency: what to check (kept up to date by its authors, widely used, licence, the exact name, to avoid look-alike packages) and who agrees it; if the project has a lock file, that it is committed and installs use only it; the command that scans dependencies for known holes, and when it runs; how and how often dependencies are updated; secret scanning; what to do on finding a security hole, such as never describing it in a public issue or commit message | `security.md` |
| 12 | Hands off | Files and folders an agent must never edit, such as generated code; actions it must never take, such as running a script that changes shared data | Rules |
| 13 | Documents to keep up to date | Which documents must change with the code | Rules |
| 14 | Running the product | The machine or operating system it needs; the commands that start and stop it, and how to tell it has started; how to reach each of its interfaces, such as a command, a web address or a port; how to put it in a given starting state, such as test data or a stand-in for an outside service; which services are safe to touch, such as stand-ins and local copies, and which are never to be touched, such as real accounts or anything shared. `/agentic:verify` relies on it | `running.md`, with the pointer "before starting or using the product: `docs/practices/running.md`" |

Left out on purpose: anything for people only, such as how to report a bug, and ways of working that exist for people rather than agents, such as sprint length, estimates and pair programming.
